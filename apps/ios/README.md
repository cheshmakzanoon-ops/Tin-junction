# Tin Junction native application — first operating railway

This directory hosts the first operating railway defined by [ADR-0006](../../docs/decisions/ADR-0006-first-operating-workbench.md). SwiftUI owns lifecycle, native save status, Help and recovery; the bundled Three.js runtime owns the miniature scene and in-memory railway. Native Application Support is the durable authority for the bounded first-loop layout format. Public Duo geometry/hinge observations remain separate from simulation state.

The app requires Xcode 27.1 and the iOS 27.1 SDK. The authored test suite currently contains **46 unit tests and four UI tests**; inspect the actual `iOS Simulator` workflow for the current implementation SHA before reporting executed results. This development slice does not accept the complete production storage, accessibility, graphics or release phases.

## Reproduce the native check

From repository root on the documented macOS runner or a Mac with the same installed toolchain:

```bash
npm ci
npm run bundle:ios
bash tools/ios/install-xcodegen.sh
.tools/xcodegen-2.46.0/xcodegen/bin/xcodegen generate --spec apps/ios/project.yml
export DEVELOPER_DIR=/Applications/Xcode_27.1.app/Contents/Developer
mkdir -p artifacts/ios
xcrun simctl list --json > artifacts/ios/simulator-inventory.json
node tools/ios/select-duo.mjs artifacts/ios/simulator-inventory.json
```

Read the selected UDID, set `TIN_SIMULATOR_UDID` to that exact value, boot it with `xcrun simctl boot "$TIN_SIMULATOR_UDID"` only if its reported state is `Shutdown`, then run:

```bash
bash tools/ios/test-simulator.sh
```

The GitHub workflow performs these steps automatically without signing. `project.yml` is authoritative; generated `TinJunction.xcodeproj` is not committed. `Resources/WebAssets` is generated by `npm run bundle:ios`; never hand-edit its output or add `.gitkeep`/README files inside it.

After successful `xcodebuild test`, the script exports the tests' genuine attachments from the exact `.xcresult` into `artifacts/ios/screenshots/`, with a `manifest.json` linking tests and filenames. The original result bundle, build log, toolchain inventory and installed attachment-command help remain in the Actions artifact. These are packaged Simulator captures, not hardware performance or final art evidence. A failed build/test remains a failure; screenshot export cannot override its exit status.

## Checkpoint and recovery contract

The engine announces `web.ready` with the `first-railway` build. Native supplies a fresh session ID through `native.bootstrap`, loads a validated local snapshot, and sends `native.layout` with the persisted checkpoint sequence. Native does not show interactive readiness until `layout.loaded` acknowledges the current session and correct document revision. The restored train has zero speed and throttle.

`layout.checkpoint` carries the session, request ID, checkpoint sequence, expected prior durable revision and validated logical document. Native sends `native.saved` only after successful atomic write and read-back verification. Failed writes produce `native.saveFailed` and leave the open edits intact. Native Save and scene inactivity request a checkpoint; ordinary web transaction/periodic checkpoints provide the main protection before suspension.

The store uses fixed private filenames under Application Support, never a path supplied by JavaScript. `current.json` contains the complete checksummed generation; `previous.json` retains its known-good predecessor. Corrupt primary data falls back to the verified previous generation with an explicit recovery notice. If both are invalid, loading fails visibly and neither is replaced with a factory layout. A later successful save after recovery preserves the damaged primary in `damaged-current.json`.

Stale checkpoints, unexpected prior revisions, cross-document writes and conflicting reused checkpoint numbers are rejected. Repeated requests while a write is pending share its original work and acknowledgement; the pending queue is capped at eight. The same structural revision may checkpoint train motion/tick changes, but metadata, scenery, track and environment edits must advance revision. A lost acknowledgement can retry an identical committed checkpoint idempotently.

Atomic replacement protects against partial application-level writes. It does not promise survival of uninstall, physical storage failure or arbitrary power loss. The tests inject interruption before write, after backup, before replacement and after replacement; actual results belong to the corresponding CI run.

## Remaining production work

The format presently represents one oval and its scenery; it is not the general track-graph format. Native multi-layout library, import/export UI, historical-format migrations, native operational accessibility inspector, production sound/haptics, app icon, signing and release packaging remain later work. Final physical-device ergonomics, VoiceOver review, sustained performance, thermals and Duo-only distribution approval also remain explicit gates. Audit the privacy manifest whenever APIs, dependencies or data handling change.

Attachment export uses Apple's public `xcresulttool export attachments` command, documented in the [Xcode 16.3 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-16_3-release-notes). The exact selected Xcode tool's help is recorded at runtime; the `--path`/`--output-path` usage is also exercised by [Chromium's maintained iOS result parser](https://chromium.googlesource.com/chromium/src/+/HEAD/ios/build/bots/scripts/xcode_log_parser.py).

See [Duo platform contract](../../docs/architecture/DUO_PLATFORM.md) and [native CI runbook](../../docs/operations/IOS_CI.md). In particular, iPhone-family targeting is not proof of Duo-only commercial distribution.
